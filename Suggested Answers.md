## LawPrix

**Q1. Walk me through the overall architecture, portal by portal.** A: The platform sits behind a single DRF API layer, with three portal types, individual clients, businesses, and verified lawyers, each getting a role on the same user model rather than separate codebases. Shared apps handle things every portal needs: auth, user profiles, notifications, the case model itself. Portal-specific apps handle what only that role sees, like the lawyer verification workflow or the business team-management views. **[Name your actual shared vs portal-specific app groupings here.]**

**Q2. Why 22 separate Django apps instead of fewer, larger ones?** A: My rule of thumb is one app per bounded concept, something with its own models, its own business logic, and a reason to change independently of everything else. Auth, case management, lawyer verification, billing, and notifications are all genuinely different concerns with different rates of change, so splitting them keeps each app testable and reviewable on its own, and keeps merge conflicts down when working across features. The trade-off is more boilerplate and more cross-app imports to manage, which is why I keep shared logic in a couple of core apps other apps depend on rather than letting every app reach into every other app's models directly.

**Q3. How do you guarantee a client-side user can never hit a lawyer-only or admin-only endpoint?** A: Every DRF viewset has explicit `permission_classes`, and I use custom permission classes that check the role claim on the authenticated user rather than relying on URL structure alone to keep people out. So even if someone guesses a lawyer-only endpoint URL, the permission check runs before any queryset logic executes and returns a 403. For anything returning a queryset, I also filter by the requesting user's own portal or ownership, so a lawyer cannot even see another lawyer's cases by ID even if they somehow got permission to hit that view type.

**Q4. If you added a fourth portal type tomorrow, say court staff, what would you need to touch?** A: I would add a new role to the user model's role choices, write a permission class for it, and decide which existing shared apps it needs read or write access to, most likely case tracking and notifications, without needing write access to lawyer verification or business billing. Because the API layer and shared apps are already decoupled from portal-specific logic, the bulk of the work is a new portal-specific app plus permission wiring, not a rewrite of the core.

**Q5. Walk me through what happens end to end when a client submits a new case.** A: The client hits a case-creation endpoint, DRF validates the payload through a serializer, and the case is saved to Supabase. That save triggers a Celery task that runs the case through the scikit-learn routing model to shortlist lawyers by case type, urgency, and specialization, and in parallel queues the RAG case-assessment task so a summary is ready by the time a lawyer opens it. Once both finish, the matched lawyers get a notification and the client sees the case appear as "under review" on their dashboard. **[Confirm whether routing and assessment actually run in parallel or in sequence in your implementation.]**

**Q6. Explain how your JWT-based role-level access control actually works.** A: I issue a short-lived access token and a longer-lived refresh token on login. The access token carries the user's role as a claim, so permission checks on the backend do not need a database hit to know what portal the request is coming from. When the access token expires, the client silently calls the refresh endpoint to get a new one without forcing a re-login, and the refresh token itself expires and forces a real login after a longer window. **[State your actual expiry windows and where the tokens are stored client-side, localStorage, memory, or an httpOnly cookie.]**

**Q7. If a lawyer's verification status changes mid-session, does their JWT get revoked immediately?** A: Honestly, a plain JWT is stateless, so it does not know a status changed until it expires and gets refreshed. If I need that change to take effect immediately, the clean way to do it is to check verification status server-side on sensitive actions rather than trusting the token claim alone for anything high-stakes, or keep the access token expiry short enough that the lag is acceptable. **[Say plainly whether you have handled this yet or whether it is a known gap you would fix.]**

**Q10. Why a classifier here rather than a rules-based scoring function?** A: A hand-weighted rules engine works until the number of case types and specializations grows, at which point the weights become brittle and hard to tune by hand. A classifier lets the model pick up on combinations of signals a human would not think to hard-code, and it is easy to retrain as more routing data comes in instead of manually re-tuning weights every time the platform adds a new specialization.

**Q19. Why does case assessment need Celery and Redis rather than running inline on the request?** A: LLM calls are slow and occasionally fail or time out, and I do not want a client's HTTP request to hang open waiting on that. Queuing the work through Celery, with Redis as the broker, means the API can respond immediately that the case was received, and the assessment gets attached to the case whenever it finishes, with the frontend polling or getting notified rather than the user staring at a spinner.

**Q23. Tell me about the security audit with the Antigravity coding agent. What did the Tier 1 vs Tier 2 framework let it do?** A: I ran an extended live audit using an AI coding agent, and rather than giving it blanket access to change production code, I set up a two-tier authority model. Tier 1 covered changes it could make autonomously, things like fixing an obvious lint issue or a clearly-scoped bug with no ambiguity. Tier 2 covered anything touching auth, permissions, or data handling, which it could flag and propose a fix for, but I had to review and approve before it landed. That split let me get the speed benefit of an agent doing the grunt work of scanning a large codebase while keeping a human gate on anything security-sensitive.
